# Relay compiler WASM research

Checked against Relay `v21.0.1` and the published `relay-compiler-playground@0.0.3` package on 2026-09-19.

The published playground WASM does not expose effective schema generation. Its public exports are `parse_to_ast`, `parse_to_ir`, `parse_to_reader_ast`, `parse_to_normalization_ast`, `parse_to_types`, `transform`, and `start`. The implementation accepts schema SDL as a string and builds an internal schema from that SDL for each operation. It does not accept a Relay config, read source files, load schema paths, or parse JavaScript/TypeScript resolver docblocks. The `get_project_config` helper hard-codes the project name to `test_project` and only deserializes feature flags and typegen settings. See the [official WASM exports and implementation](https://raw.githubusercontent.com/facebook/relay/v21.0.1/compiler/crates/relay-compiler-playground/src/lib.rs) and [crate manifest](https://raw.githubusercontent.com/facebook/relay/v21.0.1/compiler/crates/relay-compiler-playground/Cargo.toml).

The npm artifact is a browser-oriented `wasm-bindgen` package containing one JavaScript module, one declaration file, and `relay_compiler_playground_bg.wasm`. It has no Node-specific entry point. Node can use it by importing the module, reading the `.wasm` file, and calling the default initializer with its bytes. Each operation returns a JSON string whose success value is usually a debug-formatted Rust representation, rather than SDL or a normalized JSON schema. The package is published at [`relay-compiler-playground@0.0.3`](https://www.npmjs.com/package/relay-compiler-playground/v/0.0.3).

As a smoke check, the published module initialized successfully in Node when passed the WASM bytes; `parse_to_ast` and `parse_to_ir` both accepted input and returned the documented JSON-string result. This verifies that the artifact is usable from Node with a small adapter, but does not change its input contract.

Relay’s native compiler does build the composite schema from configured server schema, schema extensions, and resolver docblock IR. In the official compiler source, `build_schema` parses configured schema sources and extensions, extracts resolver docblocks, converts resolver type IR into schema definitions, extends fields, and validates the result. See [`build_schema.rs`](https://raw.githubusercontent.com/facebook/relay/v21.0.1/compiler/crates/relay-compiler/src/build_project/build_schema.rs), especially the schema source/extension and resolver extraction path around lines 122–168. This logic is in the native compiler and is not wired into the playground WASM crate.

The published `relay-compiler@21.0.1` npm package is a platform-specific native binary wrapper. Its `index.js` resolves the executable for the current platform and its `cli.js` spawns it; it does not publish a stable JavaScript schema-builder API. The native CLI can run validation and the experimental `experimental-regenerate-sub-schema` command, but those are process/file workflows rather than a read-only API returning a `GraphQLSchema` object. See the [official package README](https://github.com/facebook/relay/blob/v21.0.1/packages/relay-compiler/README.md) and [v21.0.1 release notes](https://github.com/facebook/relay/releases/tag/v21.0.1).

Conclusion: the WASM package is useful for Relay-specific document parsing, transforms, and diagnostics when an SDL string is already available. It cannot replace the schema loader’s config, schema-file, and docblock work. Native compiler execution is the authoritative route for resolver-aware behavior, but it requires a subprocess and does not provide a stable in-process schema API. A future MCP enhancement could optionally run the WASM `transform` against the loaded SDL to supplement standard GraphQL validation, while retaining the existing loader for effective schema construction.
